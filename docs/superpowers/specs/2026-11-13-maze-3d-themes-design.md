# 3D 迷宫纹理主题设计

## 意图

用户原话：「功能是对的，但我想做到更好看，比如墙面有纹理。否则我面对墙面的时候，全屏一个颜色，不好看。」随后选择：「四种我都想要，可以切换吧」——四种风格为花园树篱、砖墙、彩色积木、石头城堡，地板与天空配套调整。

现状（`maze-3d/main.js`）：墙是纯色 `MeshLambertMaterial`（紫色 `0x7e57c2`），地板是纯色，天空是纯色 `0xbfe3ff`，只有一盏环境光和一盏方向光。第一人称面对墙时整屏是同一个紫色，看不出远近和材质。

## 目标

- 新增四种主题，墙面、墙顶、地板、天空、光照、第一人称雾色都按主题配套：
  - **花园树篱 `garden`（默认）**：墙面是深浅不一的绿叶，零星点缀小花；墙顶是更深的绿叶；地板是浅色石子路；天空是浅蓝渐变。
  - **砖墙 `brick`**：错缝红砖，砖缝深色，每块砖颜色略有差异；墙顶是米色压顶石；地板是方形石板；天空是暖色调晴空渐变。
  - **彩色积木 `blocks`**：每段墙随机取一种明亮颜色（红、黄、蓝、绿、橙），墙面有积木分块线和圆角高光；墙顶有凸点；地板是带凸点的浅灰底板；天空是明亮的淡蓝。
  - **石头城堡 `castle`**：大小不一的灰色石块，石缝深色；墙顶是深灰石；地板是深色石板；天空是偏暗的灰蓝渐变（偏冒险风，但不能暗到小朋友看不清路）。
- 面对墙时画面不再是单一颜色：第一人称紧贴墙面时，画面中心区域应能取到明显多种颜色（见验收）。
- 切换方式：在视角 / 迷雾那一行下面新增一行四个主题按钮，带图标文字：「🌳 花园」「🧱 砖墙」「🧸 积木」「🏰 城堡」，当前主题高亮。每个按钮至少 44px 高，小屏可换行，不产生横向滚动。
- 切换立即生效，不重新生成迷宫，不改变小人位置、朝向、视角、迷雾、显示道路状态；切换时若小人正在移动，动画继续，不中断。
- 当前主题保存在 `localStorage` 键 `maze3d.theme`（读写包 try/catch）；读到非法值或读不到时用 `garden`。
- 起点格、终点格、道路格、视野外格的地板颜色语义不变（绿 / 红 / 红色道路 / 深色迷雾），在每个主题下都清楚可辨。

## 非目标

- 不引入任何图片文件；纹理全部在运行时用 Canvas 2D 程序生成（`THREE.CanvasTexture`）。
- 不做法线贴图、视差、阴影、后期效果、动态天空。
- 不改迷宫生成、移动、迷雾判定、寻路等游戏逻辑；不改 2D 迷宫页面。
- 不新增 URL 参数；不新增 npm 依赖。
- 小人和终点星星的外观不变。

## 反目标（做到了也算失败）

- 第一人称面对墙仍是一整屏单色。
- 纹理在远处闪烁、出现明显摩尔纹（未开 mipmap）。
- 某个主题下起点 / 终点 / 道路 / 迷雾格分辨不出。
- 切换主题导致迷宫重建、小人回到起点或动画中断。
- 切换主题后旧纹理没有释放，反复切换内存持续增长。
- 中端手机上帧率明显下降（与改动前相比，同一性能检查的平均帧时间增加超过 30%）。

## 方案

### 新模块 `maze-3d/themes.js`

ES module，不依赖 three.js 与 DOM，可在 node 中测试：

- `THEME_IDS = ['garden', 'brick', 'blocks', 'castle']`，`DEFAULT_THEME = 'garden'`。
- `parseTheme(value)`：合法 id 原样返回，否则返回 `'garden'`。
- `THEMES[id]`：纯数据，包含 `label`（按钮文字）、`sky`（渐变上 / 下两色）、`fogColor`（第一人称雾色，取天空下端色）、`hemi`（半球光天空色 / 地面色 / 强度）、`sun`（方向光颜色 / 强度）、`floorBase`（普通地板格的着色，接近白色以免压暗纹理）、`wallTint`（墙实例的默认着色）、`blockPalette`（仅 `blocks`）。
- 纹理绘制函数 `paintWall(id, ctx, size)`、`paintWallTop(id, ctx, size)`、`paintFloor(id, ctx, size)`：只调用 Canvas 2D 上下文的标准方法（`fillRect`、`arc`、`fill`、`stroke` 等）。内部用固定种子的小型伪随机数生成器，同一主题每次画出的图一致。
- `blockColorIndex(segmentIndex, paletteLength)`：用整数哈希把墙段序号映射到调色板下标，结果确定、分布均匀，相邻墙段不总是同色。
- `wallShade(segmentIndex)`：返回 0.92–1.0 之间的确定性亮度系数，用于非积木主题，让相邻墙段亮度略有差别，打破纹理重复感。

### 渲染（`main.js`）

- 纹理：每个主题首次使用时生成 3 张 256×256 的 `CanvasTexture`（墙面、墙顶、地板），设置 `colorSpace = SRGBColorSpace`、`wrapS/wrapT = RepeatWrapping`、开启 mipmap、`anisotropy = min(4, renderer.capabilities.getMaxAnisotropy())`。生成结果按主题缓存；切换到别的主题时释放（`dispose()`）不再使用的主题的纹理，只保留当前主题，以免内存增长。
- 墙：尺寸仍为 1.1×0.8×0.1，由 `BoxGeometry(1.1, 0.8, 0.1)` 建好后**一次性整理几何分组**：把 +x、−x、−y、+z、−z 五个面的索引排在一起合成分组 0（墙面材质），+y 面单独为分组 1（墙顶材质），`InstancedMesh` 使用 2 个材质的数组。这样每帧墙体只提交 2 次绘制，而不是按 BoxGeometry 默认的 6 个面组提交 6 次。此整理在性能验收之前完成。
- 墙的 UV 按世界尺寸设定纹理密度，不再沿用 BoxGeometry 每个面都铺满 0–1 的默认 UV：定义统一密度「1 个纹理周期 = 墙面方向 1.1 个世界单位 × 高度方向 0.8 个世界单位」，宽墙面（1.1×0.8）UV 为 0–1 × 0–1；窄端面（0.1×0.8）U 方向只取 0–0.1/1.1；墙顶（1.1×0.1）用墙顶纹理，U 为 0–1、V 为 0–0.1/0.8 对应的比例（墙顶纹理按 1.1:0.1 的条带内容绘制，或在 V 方向按同密度截取）。目标是三个面上的砖块、石块、积木凸点不被挤压或拉伸。不增加纹理数量。
- 墙实例颜色：每段墙都调用 `setColorAt`。`blocks` 主题取 `blockPalette[blockColorIndex(i)]`；其他主题取 `wallTint` 乘以 `wallShade(i)`。纹理为积木主题画成浅灰明暗，颜色由实例颜色乘上去。
- 地板：沿用 `instanceColor` 表达格子类型；普通格颜色改为当前主题的 `floorBase`，起点 / 终点 / 道路 / 迷雾格颜色沿用现有 `COLORS`。地板纹理画成以浅色为主，保证乘上起点绿、终点红后仍然醒目。
- 光照：把 `AmbientLight` 换成 `HemisphereLight`（天空色 / 地面色按主题），保留方向光。墙的不同朝向因此亮度不同，转角和远近更清楚。
- 天空：`scene.background` 用一张 2×256 的竖向渐变 `CanvasTexture`；第一人称雾色、`renderer.setClearColor` 都取主题的 `fogColor`。
- 小地图颜色不变。
- `applyTheme(id)`：设置墙材质贴图、墙实例颜色、地板普通格颜色、光照、天空与雾色，更新按钮高亮，写入 `localStorage`。`buildMaze` 新建墙实例后也调用这里的墙实例着色逻辑，保证重新生成迷宫后颜色仍按当前主题。
- 自动降画质时把纹理 `anisotropy` 降为 1（只改属性并设 `needsUpdate`，不重建纹理）。
- 调试对象 `window.__maze3d` 增加只读属性 `theme`（当前主题 id）与 `textureCount`（当前存活的主题纹理数量），以及：
  - `floorKindAt(row, col)`：返回该格当前实际的 `floorKind`（`floor` / `start` / `end` / `path` / `fog`），供验收确认取样格的真实类型；
  - `floorSamplePoints(row, col)`：把该格地板顶面上若干点（中心与四个内缩点）投影到屏幕，用射线检测剔除被墙、小人、星星遮挡的点，返回未被遮挡的屏幕坐标列表；
  - `wallContrast()`：在画面中心 50% 区域取样，返回亮度（Rec.601 luma）的标准差与 5%–95% 分位差，用于墙面纹理对比度验收。

### 界面

```
[切换到第一人称] [迷雾：开] [−] 视野 5 [+]
[🌳 花园] [🧱 砖墙] [🧸 积木] [🏰 城堡]
```

主题按钮沿用页面现有按钮风格，当前主题用与尺寸按钮相同的 `active` 样式。

## 测试

自动测试（`node --test tests/`）新增 `tests/maze-3d-themes.test.mjs`：

- `THEME_IDS` 恰为四个；`parseTheme` 对合法值原样返回，对 `null`、`''`、`'GARDEN'`、`'foo'` 返回 `'garden'`。
- 每个主题的数据字段齐全，颜色为合法数值。
- `blockColorIndex` 确定、在 `[0, n)` 内，对 0–999 号墙段每种颜色占比在 10%–30% 之间。
- `wallShade` 确定且在 `[0.92, 1.0]` 内。
- 用记录调用的假 Canvas 上下文跑三个绘制函数：不抛错、调用了绘制方法、同一输入两次调用的调用序列完全相同。
- 页面静态检查（`tests/maze-3d-page.test.mjs` 追加）：存在四个主题按钮；`maze-3d/` 下没有新增图片文件；`themes.js` 不含外部 URL。

浏览器验收（扩展 `tests/browser/maze3d_accept.py`，固定 seed）：

1. 四个主题依次切换，均无控制台错误，`__maze3d.theme` 与按钮高亮一致。
2. 第一人称、视野内紧贴一面墙（小人朝向一面墙站定）时，用画面中心 50% 区域采样 16×16 个点，每个主题同时满足：
   - 不同颜色数 ≥ 12；
   - `wallContrast()` 的亮度 5%–95% 分位差 ≥ 40（0–255 标度），亮度标准差 ≥ 10——只靠距离雾插值产生的渐变达不到这一对比度。
   同样条件下改动前的版本两项指标记录为基线（颜色数预期接近 1–3，分位差预期远低于 40），写入结果文件作对比。
   另外由用户人工查看第 9 步的四主题截图，确认纹理明显、观感符合四种风格；人工检查结论写入结果文件。
3. 小人移动途中切换主题：动画继续完成，位置与预期路口一致，`generation` 不变。
4. 切换主题后刷新页面，主题保持；`localStorage` 写入非法值后刷新，回退到花园。
5. 格子语义色可辨。注意 `floorKind` 的优先级是 道路 > 迷雾 > 起点 / 终点（`maze-3d/game-logic.js:189-195`），开启道路后起点 / 终点格会显示成道路色，终点在视野外时显示成迷雾色，所以不能在一个场景里同时取到五类。每个主题下按以下固定 seed 的确定场景分别取样：
   - 场景 A（迷雾关、道路关、跟随视角、小人离开起点一步）：取起点格、终点格、普通格；
   - 场景 B（迷雾关、道路开、跟随视角）：取一个道路格（非起点、非终点）与一个普通格；
   - 场景 C（迷雾开、视野 1、道路关、跟随视角）：取一个视野外格与一个视野内普通格；终点格此时也在视野外，记录其迷雾色；
   - 场景 D：从场景 C 移动小人或增大视野，使终点进入视野，确认终点格从迷雾色变为终点色。
   每个取样格先用 `floorKindAt` 确认实际类型等于预期，再用 `floorSamplePoints` 取未遮挡的屏幕点读取像素（某格没有未遮挡点则换同类型的另一格，找不到算失败）。判定：普通地板、起点、终点、道路、迷雾五类颜色**两两之间** RGB 欧氏距离都 ≥ 60（包括起点 vs 道路、终点 vs 道路这类语义色之间的比较）。
6. 反复切换主题 20 次后，`textureCount` 不超过单个主题所需的数量（墙面、墙顶、地板、天空共 4 张）。
7. 性能：与现有性能检查同条件（20×20、iPhone SE 模拟 + 4 倍 CPU 降速、同一台机器、同一 GPU 后端 `rendererName`、同一 seed 与同一 `play_rounds` 路线），每个主题平均帧时间不超过改动前基线的 1.3 倍；记录每个主题纹理生成耗时。
   - 比较必须在同画质下进行：基线与每个主题的测量都记录 `quality` 与 `downgradeCount`。只有两边测量全程都是 `quality === 'high'` 且 `downgradeCount === 0` 时，该次比较才算有效的同画质比较。
   - 如果某个主题测量期间触发了自动降画质（`downgradeCount > 0`）而基线没有，该主题的性能检查判为**失败**，不允许用降画质后的帧时间与基线高画质帧时间比较；结果文件单独报告「触发降级」及 `downgradeCount`。
   - 如果基线本身也触发了降级，则改为两边都在降级后画质下比较，并在结果文件中注明，不作为高画质性能通过的依据。
   - 另测：触发自动降画质（用现有 URL 参数 `slow=40` 模拟慢设备）后再依次切换四个主题，均无控制台错误，墙面纹理仍显示（第 2 步的颜色数与对比度指标仍满足），`theme` 与按钮高亮一致。
8. 375px 宽下主题按钮行不产生横向滚动。
9. 为四个主题各保存一张第一人称和一张跟随视角的截图到 `<repo>/.xdev/<run-id>/screenshots/`，供用户查看效果（不提交进仓库）。
